nas は Docker コンテナと通信制御を使って、エージェントが触れるファイルや接続先を制限します。利用前や権限を追加する前に、ホストにどこまで影響が及ぶかを確認してください。

## 既定の共有範囲

作業フォルダーと、選択したエージェントの既存設定・認証情報を読み書き可能で共有します。エージェントはホストの UID/GID で動くため、共有ファイルの変更はホストに残ります。コンテナ内だけの変更は終了後に残りません。

`.env` などを隠す設定は自分で追加します。追加マウントの `ro` は変更を防ぎますが、内容は読めます。共有先と非公開ファイルは[共有ファイルと秘密ファイル](/nix-agent-sandbox/configuration/files/)で指定します。

Nix は既定で自動検出され、ホストに `/nix` があると store や daemon などを共有します。不要なら `nix.enable = false` にします。共有する権限は[開発ツールと Docker](/nix-agent-sandbox/configuration/development/)で確認できます。

## プロジェクト設定の信頼

プロジェクト設定は、共有ファイル、通信、ホスト実行の権限を変えられます。環境変数や秘密値の取得コマンド、worktree の `onCreate` を通して、起動時にホストのコマンドも実行できます。

nas は `.nas/` 直下のユーザー作成 `.pkl` ファイルの内容を記録し、変更時に再承認を求めます。差分と参照先を確認してから `nas config trust` を実行します。`NAS_CONFIG_TRUST_ALL=1` はこの確認を無効にします。

設定を信頼しても、その設定が呼ぶ実行ファイルやスクリプトの安全性まで保証されません。エージェントが変更できるファイルをホストで実行すると、その変更もホストに影響します。ホスト実行の設定では、[実行ファイル・引数・作業場所](/nix-agent-sandbox/configuration/host-commands/)を合わせて制限します。

## 通信とホストへの経路

外部 HTTP(S) 通信はプロキシを経由し、セッションごとの scope とルールで認可します。既定では拒否し、設定やプリセットで許可・承認待ちに変更します。`host.docker.internal:<port>` を許可すると、プロキシからホストの TCP サービスへも到達できます。

| 追加する操作 | ホストに渡る範囲 |
| --- | --- |
| [ホストのサービスへの接続](/nix-agent-sandbox/configuration/host-services/) | 指定した localhost ポートへセッション専用ソケットで中継。接続先の DB や API の権限で操作可能 |
| [開発サーバーの確認](/nix-agent-sandbox/work/preview/) | エージェントのサービスをホストの localhost に公開。ブラウザで開いたページから他のローカルサービスへ要求を送ることも可能 |
| [ホストでのコマンド実行](/nix-agent-sandbox/configuration/host-commands/) | 実行用ソケットを通して、許可したコマンドをホストの権限で実行 |
| [認証サービスの共有](/nix-agent-sandbox/configuration/authentication/) | GPG や DBus で許可したサービスを利用。ソケットでの接続でも、署名・復号やキーリングの読み取りなどの権限を持つ |
| [GUI アプリの表示](/nix-agent-sandbox/configuration/gui/) | 専用画面のソケットと Cookie を共有。キー入力と貼り付けはエージェント側のアプリへ渡る |

接続方式がソケットでも、接続先サービスの権限は利用できます。接続先の認証・操作権限も確認してください。

## 秘密値と承認

名前付き秘密の取得と、出力マスク用の生値の読み取りはホストで行い、その生値をエージェント用のファイルとして共有しません。ただし、元の認証ファイルや通常の環境変数を別途共有すれば、エージェントはそこから値を読めます。秘密の取得元は[認証情報の受け渡し](/nix-agent-sandbox/configuration/authentication/)、送信先や注入先は[通信ルール](/nix-agent-sandbox/configuration/network/)と[ホスト実行ルール](/nix-agent-sandbox/configuration/host-commands/)で指定します。

HostExec の実行用と承認用のソケットは別です。承認用ソケットはコンテナへ渡さず、エージェント自身による承認を防ぎます。承認を再利用すると、そのセッションの同じ条件の要求にも適用されます。[承認範囲](/nix-agent-sandbox/work/approvals/)を確認して選んでください。

## 同じホストの利用者とセッション

ブラウザ UI は同じホストの利用者を信頼する前提です。別のホストユーザーからのアクセスは防がず、ターミナル、承認、履歴を操作できます。複数の利用者が共有するホストでは、この前提が適切か確認してください。UI は既定で有効で、[設定](/nix-agent-sandbox/configuration/profiles/#ui-の設定)で無効化できます。

HTTP(S) プロキシは複数セッションで再利用される場合があります。プロキシには、セッション登録情報、通信ルール、認可用ソケットを含むネットワーク実行ディレクトリを読み書き可能で共有します。

Docker in Docker の daemon と作業データはセッション専用です。公開 Docker Hub イメージの取得キャッシュは後のセッションでも再利用し、キャッシュからの取得では新たな通信承認が発生しません。補助コンテナは `--privileged` で動きます。[開発環境の設定](/nix-agent-sandbox/configuration/development/)で必要なプロファイルだけに有効化します。

## 終了後の保存データ

共有ファイルに加え、実行履歴や監査ログはホストに残ります。追加収集を有効にすると、会話やマスク前の通信本文に秘密・個人情報が含まれる場合があります。保存先と削除条件は[記録と保存期間](/nix-agent-sandbox/configuration/recording/)で確認します。

異常終了後は、出力マスク用の秘密値が一時ファイルに残る場合があります。再起動では自動回収されないため、[作業の終了と片付け](/nix-agent-sandbox/work/finish/#出力マスク用の秘密値)の手順で回収します。

コンテナの脆弱性、誤ったマウント、許可済みコマンドの悪用、同じホストの信頼できない利用者まで防ぐ保証はありません。必要な権限を使用するプロファイルに限定し、設定変更時には上の共有範囲を確認してください。
