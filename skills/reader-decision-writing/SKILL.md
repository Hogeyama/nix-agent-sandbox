# 読者の判断からの執筆

文章の材料は製品の機能ではなく、読者がそのページで終えたい判断・作業。正しい事実でも、その判断に不要なら本文に採用しない。

## 原稿前の設計

対象ページごとに、次を短く記録する。既存の編集方針があれば更新し、同じ内容を別ファイルへ複製しない。

- 読者の現在地：何をしようとして来たか。すでに知っていること。
- 読了後の判断・作業：一つの具体的な到達点。ユーザーが指定した目的を優先する。
- 必要な答えと順序：読者の疑問を、前の答えだけで次へ進める順に並べる。
- 採用する事実：各答えを支える、確認済みの材料。
- 今回載せない事実と掲載先：別の判断に使う情報の所在。

「機能を理解する」「関連ページを見つける」は、紹介ページの目的の代用にはならない。価値判断が目的なら、困りごと → 作業の変化 → 適用条件・導入負担 → 試す手順を扱う。操作が目的なら、前提 → 操作 → 結果の確認を扱う。見出しや表の型を全ページへ一律に当てない。

## 情報の採否

段落・表の行ごとに「これがないと、読者は何を判断・実行できないか」を答える。

- そのページの到達点に必要：本文に採用。
- 別の段階で必要：そこへ移す。リンクも、読者の次の行動に必要なものを選ぶ。
- 同じ答えを繰り返す：一か所に集約。
- 「機能が存在するから」「重要そうだから」だけ：採用しない。

用途の文は、製品名・機能名・実装用語を知らない人も言える困りごとにする。解決の文は、機能の名前ではなく、何を任せられ、何を自分で決めるかを書く。固有名や設定キーは、それを選択・入力する段階で説明する。

注意事項も読者の段階で配置する。実行するとデータを失う操作では実行前に示す。仕様上の共有ディレクトリなどは、その範囲を確認するページで扱う。安全性の誇張を、紹介ページへの例外追記で補修しない。誇張した主張そのものを直す。

## 執筆

設計した答えの順に新しく書く。古い文章は事実確認用の素材として使い、古い節の順序を前提にしない。

一段落で一つの疑問に答える。抽象的な効果の形容詞より、入力、操作、結果を具体化する。短さのために前提や主語を省略しない。用語の一括置換では文章の意味を修正できない。

サイト固有の文体は、そのサイトの指示に従う。見出しの名詞句化などの局所的な要望を、すべての文書に対する普遍規則にしない。

## 原稿の判定

原稿から逆に「誰の、どの判断に、何と答えているか」を書き出し、原稿前の設計と照合する。設計と違えば、言い回しの調整より先に情報選択をやり直す。

複数ページの再構成では、独立したレビュアーに編集設計と原稿だけを渡し、読者が実際に得られる答えを確認する。レビューの指摘も上の採否基準で判断する。用語が一つ不明だったことを理由に説明を増やすのではなく、読者の到達点を妨げる箇所を直す。

完了報告には、ページの目的を満たす実際の節、移した情報の所在、残る不足を示す。ビルド、リンク、設定例の検証は別に行う。文字数削減率は品質の証明にしない。

ユーザーが直近で指摘した箇所は、返答だけで直った扱いにせず実ファイルで確認する。

新規導入・手順の変更時は [評価ケース](references/evaluation.md)で回帰と別題材への適用を確認する。通常の編集で評価一式を毎回実行する必要はない。
