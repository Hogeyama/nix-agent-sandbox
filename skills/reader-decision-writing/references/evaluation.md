# 執筆手順の評価

規約への賛同ではなく、情報の採否と原稿で評価する。機械的な禁止語検査や文字数は代用にならない。

## 回帰ケース

| ケース | 読者と判断 | 入力の問題 | 合格条件 |
| --- | --- | --- | --- |
| 初見の製品ページ | 自分にも試す価値があるか | 「Docker コンテナ内で実行する CLI」「Linux と Docker が必要」で始まり、共有ディレクトリの例外が続く | 読者の作業と困りごと、それに対する具体的な変化が先。環境は導入負担として後。共有ディレクトリの列挙は概要へ。 |
| 用途の偽装 | 自分の問題に役立つか | 「認証情報が必要なコマンドをホストで実行させたい → HostExec」 | 認証情報をエージェントに読ませずに作業を任せたい、など、実装を知らなくても成立する要求。右側は作業の変化を説明し、機能名だけで終わらない。 |
| 不要な注意書き | 試す価値があるか | 「作業フォルダーへの変更はホストにも残る」「既存の設定・認証情報は共有」 | トップに残さない。正確な情報は概要に保持する。言い換えや折りたたみで同じページに残すのは不合格。 |
| 必要な注意書き | 今から作業フォルダーを削除する | 削除コマンドの後に「使用中でも削除対象」と書く | 実行前に判断できる位置に残す。トップの修正を理由に、操作ページから注意を削らない。 |
| 説明不足の手順 | 最初のセッションを起動する | 設定例の編集先や再信頼を省き「必要な通信を設定」だけで済ます | どこで何を変更し、何を実行し、何が起きれば成功かを追える。別ページを先に読むなら手順と前提を明示。 |
| 別分野への転用 | 架空のバックアップ製品を試すか | 「差分転送エンジン」「SQLite index」「保存場所」の素材だけで紹介を書く | 機構を主役にしない。素材で裏づけられない復元保証や所要時間を作らない。掲載しない情報と置き場所を判断できる。 |

## 評価方法

- この表の期待結果を読む前に、実際の原稿を読者として要約する。期待結果と実際の読み取りを後で比較する。
- 新規作成・大きな変更では、別の書き手に手順と別題材の事実だけを渡す。正解例は渡さない。
- 原稿の完成後に、目的に対する不足・余計な情報・前提の飛躍を確認する。問題があればどの節で何を判断できないかを記録する。
- 一度の成功から常に良い文章が書けるとは結論しない。新しい失敗は、禁止語ではなく判断条件の不足として修正する。

## 適用後の確認（2026-09-05）

nas のトップは「用途」でファイル非公開・通信制限・認証付き作業を示し、「対応環境」「起動までの作業」で導入条件と設定の負担を示す構成に変更した。HostExec を用途名にせず、共有ディレクトリの説明は概要へ移した。独立レビューでも、読者が自分の作業に当てはめて試す価値を判断できると確認した。

操作ページでは、worktree の未コミット変更を失う説明を削除コマンドより前に配置した。クイックスタートには編集先・通信設定・再信頼・起動・応答による成功確認を揃えた。トップの注意書きを減らす判断と、操作前に必要な注意を残す判断を両方確認した。

別題材の試験では、独立した書き手にこの手順と架空のバックアップ製品 trail の事実だけを渡した。正解例や nas の原稿は渡していない。生成された紹介文は「Git にコミットする前の変更や、まだ Git に追加していないファイルを、少し前の状態に戻したい」から始まり、SQLite の索引や保存パスは紹介に採用しなかった。Linux・別のローカルディスク・初回の全量コピーは利用条件として残した。素材にない復元保証や所要時間も加えていない。

同じ試験の削除手順は、取り消せない影響 → 一覧 → dry-run → 実行 → 削除後の確認の順になった。不要な注意を外す指示が、必要な操作警告まで削る結果にはならなかった。

この記録は nas への適用と一つの別題材の結果であり、あらゆる文章の品質を保証するものではない。ページ別のレビュー結果と技術検証は `docs-site/editorial/review.md` に記録する。
