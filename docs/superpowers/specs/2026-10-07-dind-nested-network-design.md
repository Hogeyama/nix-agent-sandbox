# Bash の隔離内から DinD を使う

## 利用者ができること

nas の DinD を有効にした状態で、Claude Code の Bash sandbox の中から従来どおり `bun test` などを実行する。Testcontainers の Docker API 操作と、起動したコンテナの公開 TCP ポートへの接続が動く。`excludedCommands` や追加のコマンド接頭辞は不要にする。nas が生成する `/nas-sandbox` スキルに、動作条件と失敗時の確認方法を載せる。

## 構成

nas と DinD が共有するネットワーク空間に、Unix ソケットでだけ要求を受ける中継を置く。接続先はセッション専用の Docker API と、その Docker が実際に公開している TCP ポートに限定する。任意のホスト名、IP アドレス、nas 側の未公開ポートへの接続は提供しない。

nas が提供する Bash ラッパーで、コンテナ起動時に記録したネットワーク namespace と現在の namespace を比較する。同じなら従来どおり実行する。異なる場合は、その namespace 内で中継を準備してから Bash を実行する。同じ namespace の子 Bash は既存の中継を利用し、さらに namespace が変わった場合は別の中継を作る。`SANDBOX_RUNTIME` などの環境変数を権限判定には使わない。

内側の中継は Docker API を Unix ソケットで提供し、子プロセスの `DOCKER_HOST` をそこへ向ける。公開ポートは内側の `127.0.0.1` に再現する。API の応答と公開ポートの準備を同期し、Testcontainers が公開ポートを知ってから最初に接続するまでの競合を避ける。既存のポートと衝突した場合は別サービスへ接続させず、明確なエラーにする。

マスク機能と中継の有効条件を分離し、マスクを無効にしても DinD の中継は使えるようにする。既存の sumi の argv、終了コード、シグナル、出力マスク、入れ子抑止と、固定された agent hook の例外を維持する。通常の起動、対話シェル、Dev Container の共通 entrypoint に組み込む。

## 境界と寿命

- 中継が使う Docker API は、ホスト Docker ではなく、その nas セッションの DinD に固定する。
- DinD の通信には引き続き `docker.networkScopes` を適用する。agent のトークン、承認、OAuth を渡さない。
- 公開ポートへの接続は Docker の現在の状態から検証する。停止・削除したコンテナへの転送を残さない。
- 中継の制御を悪用して任意の nas loopback サービスや外部宛先へ接続できないようにする。Docker API の固定入口とデータ接続の認可を分離する。
- 内側の中継は最外周の対象 Bash の終了時に閉じる。子プロセスの終了コードとシグナルを維持する。初期化不能・途中の中継断線を、隔離を外すフォールバックで処理しない。
- TTY を持たないツール実行では専用のプロセスグループを管理し、終了時に残った子孫も終了させる。対話 TTY では既存の Bash のジョブ制御を維持する。Bash が終了後も残すバックグラウンドジョブを追加で強制終了する契約にはせず、Bash の終了時には中継を閉じる。明示的なシグナルは、その時点の Bash と子孫に転送する。
- 初回は Linux、IPv4 loopback、公開 TCP ポートを対象にする。UDP と、コンテナからテストプロセスへの逆向き接続は対象外。

### 公開ポートの検証

DinD の private IP は rootlesskit の内側にあり、agent 側から直接は接続できない。そのため rootlesskit が公開した loopback listener を中継する。Docker API の start/restart を gateway で受け、要求前には存在せず、成功後のコンテナ情報に対応する listener の inode だけを登録する。各接続の前後に Docker の公開状態と同じ listener であることを再確認し、検証前にはアプリケーションのデータを流さない。停止や listener の置換後は登録を失効させる。

gateway を経由せずに起動したコンテナは転送候補から外す。隔離内の Docker 操作自体は使えるようにし、隔離内からの再起動で登録できるようにする。未登録の公開ポートを持つ稼働中コンテナの inspect は、使えないポートを返す代わりに再起動の必要を示すエラーを返す。start/restart と公開ポートの列挙を同期し、起動成功後・登録前の状態を別の要求が観測しないようにする。

この検証は観測した listener の同一性を使うもので、カーネルから所有者の証明を得るものではない。外側の namespace で任意のプロセスを実行できる別の攻撃者が、起動成功から最初の観測までに listener を置き換えるケースは保証しない。内側の Bash は外側の listener を直接作成・置換できず、中継も任意の転送先を受け付けない。外側の敵対的プロセスまで対象にする場合は、sidecar 側の協力による所有者確認が別途必要になる。

### 終了処理の設計補足

レビューで、計画の「すべての子プロセスを終了する」という表現が、既存の対話 Bash のジョブ寿命まで変更することが分かった。今回の目的は中継の追加と既存のシェル動作の維持なので、その表現を中継が所有するリソースと非 TTY のツール実行に限定した。対話 TTY では、通常終了後のバックグラウンドジョブの存続と中継の閉鎖を別々に検証する。

## 検証

Unix API、動的な公開 TCP ポート、同一 namespace の入れ子と別 namespace の入れ子、同時実行、ポート競合、停止・削除、子の失敗・シグナル・中継切断を検証する。固定 API 以外の任意 TCP 接続が拒否されることも確認する。

実際の bwrap と Docker を使い、通常の namespace では接続できるが内側では直接接続できない対照を置く。ラッパー経由で Testcontainers がコンテナを起動し、公開ポートを使い、後片付けできることを確認する。通常の Bash と出力マスクの既存テストも維持する。最終確認は AGENTS.md と post-change-checks に従い、制限付き実行とホスト実行を順に行って結果を分けて報告する。

## なぜこのアプローチを選んだか

既存の host–nas の port-forward と同様に、Unix ソケットを使って隔離境界をまたぐ。公開ポートの中継だけを足すため、Bash の外向きネットワーク制限を維持できる。

`node` や `bun` の除外は任意のテストコードを隔離の外で実行するため採用しない。専用コマンドの手動指定と `CLAUDE_CODE_SHELL_PREFIX` の追加設定は、既存の Bash ラッパーへ組み込むことで不要にする。srt 固有の環境変数だけに依存せず、必要な性質である namespace の違いを判定する。
