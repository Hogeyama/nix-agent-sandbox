# strait の認証情報をホスト側で上書きする

## この設計で判断すること

読み手は strait の認証情報の流出経路を修正する開発者・レビュアーを想定する。送信時の認証情報を誰が決めるか、srt にどこまで任せるか、何を検証すれば変更を採用できるかを定める。

前提文書は `contrib/strait/DESIGN.md`、`contrib/strait/SECURITY.md`、`docs/architecture/threat-model.md`、`skills/security-constraints/SKILL.md`。コンテナ固有の制約は bubblewrap にそのまま適用せず、秘密をホスト側に保持することと承認経路の隔離を維持する。

## 問題

srt 0.0.77 は、送信先に対応する sentinel を要求のヘッダーと本文から探し、実トークンに置換する。上流が本文を反射すると、実トークンがサンドボックスへ戻る。また、この置換だけでは、攻撃者が持ち込んだ別のトークンがそのまま上流に届く。後者は脅威モデルの「系統2: srt」「A1b」の制限である。

現在の strait は、認証ヘッダーの値が発行済み sentinel と一致するかを調べ、別のトークンを拒否している。しかし、認証以外のヘッダーや本文への置換は止めていない。

## 決定

許可された要求の認証情報は、送信先に対応するホスト側の設定で上書きする。クライアントが送った値と sentinel の一致は、認証情報の選択にも要求の許可にも使わない。クライアントが認証ヘッダーを省略した場合も、ホスト側で認証情報を設定する。

srt のマスクはサンドボックス内の環境変数を隠すために使う。全認証情報の `injectHosts` を明示的な空配列にして、srt のヘッダー・本文の sentinel 置換を無効にする。本文、URL、認証用ではないヘッダーは、この認証処理では変更しない。

これにより、任意のデータを実トークンへ変換させる経路と、クライアントが認証主体を選ぶ経路を分けて塞ぐ。sumi の出力マスクのような文字列全体の走査は行わない。

## 認証情報の選択

| 送信先 | ホスト側で設定するヘッダー |
| --- | --- |
| `api.github.com` | `Authorization: Bearer <GH_TOKEN>` |
| `github.com` | `Authorization: Basic <base64(x-access-token:GH_TOKEN)>` |
| `api.anthropic.com` | `CLAUDE_CODE_OAUTH_TOKEN` があれば `Authorization: Bearer ...`。なければ `ANTHROPIC_API_KEY` で `x-api-key` を設定 |
| `hosts` で認証情報を設定したホスト | 設定済みの `header` と `scheme` を使い、ホスト環境の `env` の値を設定 |

Anthropic の両方の認証情報がある場合は OAuth を優先する。この選択はクライアントのヘッダーには依存しない。もう一方の認証ヘッダーは除去する。

上書き前に `Authorization` と `x-api-key`、追加ホストの設定済み認証ヘッダーを除去し、選んだ認証情報だけを設定する。重複ヘッダーや scheme の大小文字、クライアントの token の内容で認証主体が変わらないことを保証する。

固定ホスト用の認証情報がホスト環境にない場合は、認証ヘッダーなしの要求は従来どおり匿名で判定する。認証ヘッダーが付いた要求は拒否し、クライアントの値へフォールバックしない。追加ホストの必須環境変数がない場合は、従来どおり起動時に拒否する。

認証を設定していない追加ホスト、Artifact のホスト、hostexec では認証情報を注入しない。これらに認証ヘッダーを付けた要求は拒否する。

Cookie、URL の userinfo、query の `access_token` は引き続き拒否する。body による認証など別経路で認証主体を切り替えられる API は、追加ホストとして安全に利用できる前提を満たさない。repo、操作、GraphQL の検査と人間の承認は維持する。

## 実装の境界

送信先ごとの認証情報の組立てと上書きは `contrib/strait/src/core/` に置く。秘密の実値を `policy.decide()` や承認 UI、判定理由に渡さない。`policy.decide()` は、値の一致ではなく、認証方式を上書きできる送信先か、別経路の認証がないかを検査する。

srt へのパッチは、既存のヘッダー更新箇所からホスト側の上書き関数を呼べるようにする小さな接続にとどめる。TLS を終端した要求で、`filterRequest` の許可・承認後、hop-by-hop ヘッダーを除去した後に実行する。本文を読み込む範囲は増やさず、プロキシを新設しない。上書き関数が失敗したら上流へ送らず、実値を含み得る例外内容をクライアントに返さない。

`Connection: authorization` のような要求でも上書き結果が消えず、クライアントの認証情報が復活しない順序にする。ホスト名はクライアントの Host ヘッダーではなく、srt が検証した接続先を使う。

新しいパッチが欠けた構成では起動しない。Nix ビルド時にもパッチを検査する。`injectHosts: []` と組み合わせ、上書きが働かないときに従来の広範囲の置換へ戻らない。

sentinel と実値を突き合わせて policy 用の識別値を収集する処理は不要になる。マスク自体の成立確認は残し、git が認証ヘッダーを送るためのダミー設定と、hostexec の出力マスクも維持する。

## 検証する性質

実秘密や外部の echo サービスに依存せず、試験用の値とローカルの上流で送信内容を確認する。

- クライアントが認証ヘッダーを省略、ダミーを指定、別のトークンを指定した各場合で、上流には同じホスト側の認証情報が届く。
- 本文と認証用ではないヘッダーに sentinel があっても、そのまま届く。本文は通常の送信、チャンク境界に sentinel がまたがる送信、body を持つ GET を含む。
- 別ホストの sentinel を送っても実値に変わらない。設定された認証情報がない場合、クライアント指定の認証情報は上流に届かない。
- Git の Basic 認証、Anthropic の認証方式の選択、追加ホストのカスタムヘッダーが、クライアントの値に依存しない。
- 重複ヘッダーと `Connection` によるヘッダー指定が、認証主体の変更や注入の欠落につながらない。
- deny、承認待ち、承認拒否では上流に届かず、承認された要求にだけ上書きする。
- srt のマスク対象は引き続きサンドボックス内でダミーになり、送信時の自動置換は無効である。パッチ欠落は起動時に検出する。

既存の `tests/probe.sh` の「別トークンは拒否」という期待値を上書きの動作に合わせる。README、DESIGN、SECURITY の説明も更新する。変更後は strait の対象テスト・型検査・パッケージの検証に加え、リポジトリの規則どおりルートで `bun run test` と `hostexec bun run test` を順に実行し、各環境の失敗・スキップを区別して報告する。

## 保証しないこと

上流が認証ヘッダーそのものを反射すれば、実トークンは依然として戻り得る。これは認証情報を上流へ渡す以上残る信頼条件である。「エージェントが本物のトークンを取得することもできない」という現在の README の断定は修正する。レスポンス全体のマスクは今回の対策に含めず、上書きによって反射全般を防げるとは説明しない。

脅威モデルの通常の srt に対する評価は変更しない。今回変わるのはパッチとポリシーを組み込んだ strait である。

## なぜこのアプローチを選んだか

認証情報をホスト側で上書きすれば、通信の認証主体がクライアント指定の文字列から独立する。これは脅威モデルで nas の A1b を評価している制御と一致する。マスクと認証情報の付与も、それぞれの役割に分けられる。

認証ヘッダー内に sentinel の置換を限定する案では、認証情報の選択を依然としてクライアントに依存し、発行済み sentinel の照合と対応付けが残る。レスポンスのマスクを主対策にする案では、符号化や分割による返却を一般に防げず、不要な箇所へ実値を送る原因も残るため採用しない。
