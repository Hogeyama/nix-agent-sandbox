# nas User Documentation Site

**Status:** Approved

**Date:** 2026-09-04

## 目的

現在の `README.md` は、製品紹介、インストール、設定、機能ガイド、運用手順、
セキュリティ説明を 1 ファイルに収めており、約 900 行ある。初めて使う人は開始手順を
見つけにくく、既存ユーザーも目的の設定や運用コマンドへ移動しにくい。また、長い
README の一部には、現在の `Schema.pkl` や実装と一致しない旧設定例が残っている。

利用者向け情報を、検索とナビゲーションを備えた日本語の静的サイトへ再構成する。
README は製品の入口へ戻し、概要、最短のインストール、最小のクイックスタート、
ドキュメントサイトへのリンクだけを 100〜150 行で提供する。

## 対象読者と範囲

対象は nas を導入、設定、運用する日本語話者である。初版は日本語だけを提供し、
将来の多言語化を前提としたディレクトリ階層や翻訳ワークフローは設けない。

初版に含めるもの:

- インストールとクイックスタート
- profile、ユーザー共通設定、プロジェクト設定の基本
- 利用者が有効化できる主要機能の説明、主要設定、設定例
- よく使う構成のレシピ
- サブコマンドを使った日常運用
- nas の信頼境界、機能別リスク、推奨事項、既知の制約
- 既存の Network、HostExec、UI、セッション関連スクリーンショット

初版に含めないもの:

- ADR、内部アーキテクチャ、TODO、superpowers の spec / plan
- 開発者向けビルド・コントリビューションガイド
- 旧設定形式の利用ガイドや移行履歴
- 全設定キーを自動生成する網羅的な API リファレンス
- ブログ、バージョン別ドキュメント、サイト分析、コメント機能
- 英語版および多言語切り替え
- Git 署名の HostExec レシピ

設定の完全な定義が必要な読者には、各機能ページからリポジトリ内の
`src/config/Schema.pkl` へリンクする。

## 情報設計

サイトのサイドバーは、利用者の作業順と目的で次のように構成する。ページタイトルは
日本語、URL slug はリンクを安定させるため英字とする。

```text
はじめに
├── nas とは
├── インストール
├── クイックスタート
└── 設定の基本

機能ガイド
├── ファイル隔離・マウント
├── ネットワーク制御
├── localhost ポート転送
├── HostExec
├── シークレット・認証情報
├── Nix 統合
├── Docker in Docker
├── Worktree
├── セッション・通知
├── X11 / xpra
├── UI daemon
└── Observability

レシピ
├── .env を隠してコマンドをホスト実行
├── ./gradlew など相対パスコマンドの移譲
├── proxy 環境変数を参照しないツール
├── Codex の keyring
└── X11 アプリ

運用
├── Docker イメージの再ビルド
├── Worktree / Sidecar の掃除
└── Network / HostExec 承認

セキュリティ
├── 設計思想と信頼境界
├── 機能別リスク
├── 推奨設定
└── 制約・注意事項
```

実装を確認した結果、独立した説明を必要としない小機能は、最も近いページの節として
扱ってよい。反対に、一つのページが複数の異なる利用目的を持つほど長くなる場合は、
上記のグループを維持したままページを分割する。

## ページの構成

トップページは製品ランディングページではなく、マニュアルの入口とする。常に
サイドバーを表示し、「インストール」「設定を作る」「起動する」の 3 ステップを本文の
最初に示す。そこから設定の基本と各機能ガイドへ進めるようにする。

各機能ページは、読者が別のページ構成を覚えなくてよいように次の型を使う。

1. **どんな機能？** — 利用者が得られる結果を説明する。
2. **いつ使う？** — 代表的な用途と、有効化すべきでない場面を示す。
3. **主要な設定項目** — 日常的に使うキー、値、既定動作だけを表で示す。
4. **最小の設定例** — コピーして調整できる、現行 `Schema.pkl` に適合した例を示す。
5. **注意点・セキュリティへの影響** — 信頼境界が変わる箇所を設定の直近で警告する。
6. **関連ページ** — レシピ、運用、セキュリティ説明への導線を示す。
7. **全定義を見る** — `Schema.pkl` の該当ソースへリンクする。

全ページで同じ見出しを形式的に置く必要はない。「いつ使う？」が「どんな機能？」の
数文で明らかな場合などは統合できる。ただし主要設定、動作する設定例、セキュリティへ
の影響は省略しない。

## 内容の移行と正確性

README の文章を行単位で機械的に移すことはしない。ページを書く前に、関連する
`Schema.pkl`、CLI 実装、stage / service、およびテストを確認し、現在の振る舞いを正と
して説明を書き直す。

具体的には以下を守る。

- 旧 `network.allowlist` のように現行スキーマと矛盾する例は移植せず、現在の
  `network.scopes` / rules モデルに合わせる。
- 同じ説明は一つのページへ集約し、他ページは節アンカーへリンクする。
- README の情報を削除するのは、移動先ページが完成してからにする。
- 設定例は、説明上不要な設定を含めず、最小の自己完結した例にする。
- 実装から断定できない保証や安全性は記載しない。
- セキュリティ説明は、コンテナにシークレットの生値をマウントしないこと、HostExec の
  control socket をコンテナへ公開しないこと、ホスト実行出力もマスク対象であること、
  ホストサービスへのアクセスを明示的な Unix socket に限定することを崩さない。
- シークレットの実値、ローカルパス、監査データなどをビルド成果物へ取り込まない。

README の短縮後も、インストール直後に `nas config init` と `nas` を実行する最短経路は
README 単体で理解できる状態を維持する。

## 技術構成

静的サイトには Astro Starlight を使う。サイト固有のファイルは `docs-site/` に置き、
既存の `docs/` にある内部資料と公開対象を物理的に分ける。

```text
docs-site/
├── astro.config.mjs
├── public/
│   └── images/
└── src/
    ├── content.config.ts
    ├── content/docs/
    │   ├── index.mdx
    │   ├── getting-started/
    │   ├── features/
    │   ├── recipes/
    │   ├── operations/
    │   └── security/
    └── styles/custom.css
```

Astro と Starlight の依存関係はルートの `package.json` の `devDependencies` に追加し、
既存の `bun.lock` で固定する。ルートには `docs:dev` と `docs:build` script を追加する。
別の package manager、入れ子の lockfile、Python 環境は導入しない。

Starlight の標準レイアウト、レスポンシブサイドバー、ライト / ダークテーマ、ページ内
目次、アクセシビリティ対応を利用する。独自 UI は作らず、緑系アクセント、簡素な
`nas` ワードマーク、既存画像を表示するための最小限の CSS だけを追加する。

検索には Starlight 標準の Pagefind を使う。ルート locale を日本語 `ja` に設定し、
外部検索サービスや API key を必要としない、ビルド時生成の全文検索にする。

## GitHub Pages と CI

公開先は `https://hogeyama.github.io/nix-agent-sandbox/` とし、Astro の `site` と `base` を
このリポジトリ配下の URL に合わせる。内部リンクと画像参照は base path を含む公開形態
で動作させる。

GitHub Actions は次の二つの責務に分ける。

- 既存 PR CI では `docs:build` を実行し、本文、設定、内部リンク、アセット参照が
  ビルドできることを検証する。
- Pages workflow は `main` への push と手動実行でサイトをビルドし、Pages artifact を
  `actions/deploy-pages` で公開する。

Pages workflow には `contents: read`、`pages: write`、`id-token: write` の必要最小限の
権限だけを与える。ビルドは静的かつ公開情報だけで完結させ、repository secret や
サンドボックス実行時のデータを参照しない。

GitHub リポジトリ設定で Pages の Source を GitHub Actions にする操作は、コード外の
一度だけのセットアップとして実装後に案内する。

## 失敗時の扱い

- 不正な frontmatter、壊れた内部リンク、存在しない画像は、公開後の欠落として許容
  せず `docs:build` を失敗させる。
- Pages deployment は build job の成功後だけ実行する。ビルド失敗時は直前の正常な
  Pages 公開物を置き換えない。
- Pagefind の検索 index が生成されない場合は、見た目だけ公開可能でもビルド確認を
  合格にしない。
- 内容の正確性を自動判定できない箇所は、関連実装とテストへの照合を必須にする。
- GitHub Pages の外部設定が未完了でも、ローカル build と Pages artifact 生成までは
  独立して検証できるようにする。

## 検証

実装後に以下を確認する。

1. `bun run docs:build` が成功し、Pages 用 base path を含む静的成果物と Pagefind index が
   生成される。
2. 生成サイトをブラウザで開き、トップ、クイックスタート、代表的な機能ページ、
   セキュリティページにサイドバーから到達できる。
3. 日本語で「ネットワーク」「HostExec」「xpra」を検索し、対応するページまたは節が
   結果に現れる。
4. デスクトップとモバイル幅、ライトとダークテーマで、ナビゲーション、コード例、
   表、警告、画像に欠落や横方向のはみ出しがない。
5. README が 100〜150 行で、概要、最短インストール、最小クイックスタート、公開
   サイトへのリンクを単体で提供する。
6. README と公開サイトに旧設定形式や、現在の `Schema.pkl` で無効な設定例が残って
   いない。
7. リポジトリ標準の format、lint、型検査、unit test、最後の full test が成功する。

## 完了条件

- 利用者向けの全ページが `docs-site/` にあり、内部資料は Pages artifact に含まれない。
- サイドバーからすべての主要機能、レシピ、運用、安全性の説明へ到達できる。
- 各機能ページが、概要、主要設定、動作する最小例、セキュリティ影響を提供する。
- README は 150 行以内で、サイトへの入口として機能する。
- 日本語全文検索が生成サイトで動作する。
- GitHub Pages workflow と PR build check が構成されている。
- 現在のコードとスキーマに反する説明や設定例が残っていない。

## なぜこのアプローチを選んだか

今回の問題は文章量そのものより、異なる利用目的の情報が一つの README に直列化され、
目的からページへ移動する手段がないことである。機能別ページ、常時見えるサイドバー、
日本語全文検索を組み合わせることで、初めて使う人の順次学習と、既存ユーザーの
ピンポイントな参照を同じサイトで支えられる。

Starlight はマニュアル中心の標準レイアウト、Pagefind、レスポンシブ表示、ライト /
ダークテーマを標準で提供する。nas の既存 Bun / TypeScript toolchain で管理でき、独自
フロントエンドを保守せずに必要な体験を得られる。公開サイトを `docs-site/` に分離する
ことで、ADR や作業メモを誤って公開する危険も減らせる。

網羅的な設定表より機能別ガイドを選ぶのは、利用者の問いが「このキーは何か」より
「この機能をどう安全に使うか」だからである。各ページの設定例のそばに信頼境界の変化
を置く構成は、中央のセキュリティ章だけに注意事項を集めるより見落としにくい。

## なぜ他のアプローチを選ばなかったか

- **README を複数の Markdown へ分けるだけ:** GitHub 上で読むことはできるが、横断検索、
  一貫したサイドバー、ページ内目次がなく、目的の情報を探しにくい問題を十分に解決
  しない。
- **VitePress:** Bun / TypeScript と馴染み、構成も軽いが、標準の MiniSearch で日本語
  検索品質を担保するには追加の tokenizer 調整が必要になる。Starlight の Pagefind は
  日本語の空白なし文を標準で分割できる。
- **Material for MkDocs:** 日本語検索とマニュアル UI は成熟しているが、Bun プロジェクト
  に Python package と別 lockfile を持ち込む。今回必要な機能は Starlight で満たせる。
- **独自サイト:** 見た目を完全に制御できる一方、検索、ナビゲーション、レスポンシブ、
  アクセシビリティを自前で保守する必要がある。nas の機能説明を改善する目的に対して
  過剰である。
- **Schema.pkl から全設定リファレンスを生成:** 完全性には優れるが、利用場面と安全性を
  説明する機能別ガイドを置き換えない。生成器の設計と保守も初版の目的から外れる。
