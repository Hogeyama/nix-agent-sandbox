# nas コンテナで nix-direnv のキャッシュを使う

状態: 2026-09-13、nix-direnv の標準動作に寄せる簡素化を承認済み。
実装までの人間レビューはユーザーの指示により省略する。

## この設計で決めること

同じ作業場所で nas コンテナを起動するときに、`use flake` の再評価を減らす。
保守する人が、nas の担当範囲と nix-direnv に任せる動作を判断できる設計とする。
一般的な direnv の使い方は公式ドキュメントに任せ、利用ガイドは追加しない。

## nas が担当すること

- 固定した nix-direnv 3.2.0 の上流スクリプトとライセンスをイメージに収録する。
  ビルド時にハッシュを検証し、コンテナ起動時にはダウンロードしない。
- 許可済みの `.envrc` を読み込む前に、direnv のライブラリ経路へ初期化処理を設置する。
  `DIRENV_CONFIG`、`XDG_CONFIG_HOME`、HOME の順で設定先を決め、利用者の
  `direnvrc` を上書きしない。同じ内容なら設置済みファイルの時刻を更新しない。
- direnv の `direnv_layout_dir` 拡張点で保存先を分離する。既定では
  プロジェクトの `.direnv/nas/` 配下を使い、ホスト側の profile と混在させない。
  HOME、作業ディレクトリ、拡張バージョンを区別する。
  ワークスペース内なので、同じ作業場所ならコンテナを作り直しても再利用できる。
- 既存の allow / deny 判定をキャッシュ読み込み前に実施する。
  未許可の `.envrc` を実行したり、自動で許可したりしない。

保存先の設定は direnv の layout 全般に適用する。
プロジェクトが独自に `direnv_layout_dir` 関数を定義した場合は、その設定が優先される。
共有領域の外へ保存先を変更した場合、コンテナ削除後の再利用は保証しない。

## nix-direnv に任せること

Nix の評価、profile の保存、監視対象による更新判定、手動更新、失敗時の動作を
上流の実装に任せる。nas は `use_flake` / `use_nix` をラップせず、内部変数や
キャッシュファイルを操作しない。

再評価に失敗した場合は、nix-direnv 標準の動作として以前の環境へ戻ることがある。
起動を必ず失敗させる独自処理は設けない。手動リロードも同梱バージョンの動作に従い、
監視対象外の変更を必ず再評価するという nas 独自の保証は設けない。
`.envrc` と `shellHook` の実行も上流の通常動作に従う。

## 検証範囲

nas が追加する読み込み・保存先分離と、異なるプロセスからのキャッシュ再利用を確認する。
テストは呼び出し回数やパスで判定し、待ち時間や速度に依存させない。
上流の無効化・失敗・手動リロードを再実装するテストは維持しない。
既存の起動許可、argv、環境変数の順序、plain `.envrc` の検証は維持する。

fmt、lint、型チェックと、ユーザー指定の最終全テストを一度実行する。
Docker イメージを再ビルドしていなければ、その範囲は未検証と報告する。

## なぜこのアプローチを選んだか

キャッシュ機構を nix-direnv に任せることで、nas が保守するコードを導入と保存先の
設定に限定できる。既存のワークスペース共有で永続化でき、新しいボリュームも不要になる。

## なぜ他の案を選ばなかったか

Nix 呼び出しの独自ラッパー、強制失敗、キャッシュの手動削除は、上流の実装への依存と
検証負担を増やすため採用しない。ホストと profile を共有すると環境固有のパスを
持ち込むため、保存先の分離は残す。
