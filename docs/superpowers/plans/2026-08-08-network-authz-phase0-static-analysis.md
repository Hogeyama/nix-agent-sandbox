## 実装の要点

### 保守側に倒す

軸ごとの判定は、**証明できたときにだけ**「交差しない」「包含する」と結論する。証明でき
なければ「交差する」「包含しない」に倒す。どちらも設定エラーの側に落ちるので、判定の
不完全さが認可の緩みにならない。**この方向を逆にしないこと。**

### 合併に対する包含は不完全でよい

`paths` は複数パターンの合併なので、包含は「A のすべてのパターンが B のいずれか 1 つに
包含される」で判定する。`{n}` を `["a","b"]` に制約した 1 本が `/a` と `/b` の 2 本の
合併に包含される場合を取りこぼすが、仕様がそれを許容している。完全な判定を目指さないこと。

### `format` は格子である

`"opaque"` はボディを解析しないので `"json"` と `"none"` の**両方を包含する**。
`"json"` と `"none"` は交わらない。仕様の表を見ること。「format が違えば比較不能」は
**誤り**であり、前設計の記述が残っていたのを訂正済みである。

### 軸の独立性に依存している

メソッド / パス / ボディは独立なので、直積として軸ごとに判定して合成できる。これが成立
するのは**ボディ条件の右辺に capture を置けない**からである。この制限を緩める提案が出て
きたら、この分解が壊れることを指摘すること。

## テスト

**プロパティテストが本命の安全網である。** 実データ（`.nas/config.pkl`）は 40 ホストの
ベタ allow がほとんどでルールが無く、検査器がほとんど動かないので、通しても安心材料に
ならない。

`fast-check` は入っていない。依存を増やさず、seeded PRNG で生成器を手書きする
（この repo の依存は `effect` / `zod` / `solid-js` / `xterm` のみで、この方針を維持する）。

生成するもの: ランダムな `Match`（メソッド集合、パスパターン、captures 制約、ボディ条件）と、
ランダムなリクエスト（メソッド、パス、ボディ）。

検証するプロパティ:

| プロパティ | 内容 |
| --- | --- |
| 包含の健全性 | A ⊆ B と判定したら、A が受理する生成リクエストは必ず B も受理する |
| 交差の健全性 | 交差しないと判定したら、両方に一致する生成リクエストが存在しない |
| 反射性 | A ⊆ A |
| 推移性 | A ⊆ B かつ B ⊆ C なら A ⊆ C |
| 反対称性 | A ⊆ B かつ B ⊆ A なら受理集合が等しい |
| 証人の妥当性 | 交差すると判定したとき、構成した証人が実際に両方に一致する |

**推移性は自明ではない。** `**` と `captures` が絡む場合に成立するかを確かめること。
**成立しなければ「候補を特異度の降順に評価する」という評価順の定義が崩れる**ので、その
場合は実装を続けず、仕様の問題として報告すること。
