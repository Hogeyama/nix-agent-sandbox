## 仕様の「段階 3」のうち、すでに終わっているもの

**静的解析は段階 0 で作り終えている。** 段階 3 で新しく書く判定アルゴリズムは無い。

| 済んでいるもの | 場所 |
| --- | --- |
| `equals` / `oneOf` / `graphql` を持つ `BodyMatch` 型 | `authz/types.ts` |
| `equals` → 1 要素 `oneOf` への正規化 | `authz/relation.ts` の `normalizeBody` |
| ボディ条件の交差・包含 | 同 `bodiesIntersect` / `bodySubsumes` |

| 交差の証人 | `authz/witness.ts` |

いずれもプロパティテスト付きである。段階 3 の作業は **これらを設定と実トラフィックに
配線すること**であって、書き直すことではない。

値条件が今どこで落ちているかは 4 か所に限られる。

1. `src/config/Schema.pkl` の `class BodyMatch` — `format` しかない
2. `authz/config.ts` の `BodyMatchConfig` — `format` しかない
3. `authz/resolve.ts` の `decide` — `evaluateBody({format, pointers: new Map(),
   graphql: null}, ...)` と、解決時に値条件を捨てている
4. `nas_addon.py` の `_MATCH_KEYS = {methods, paths, bodyFormat}` — 解決済み
   ドキュメントの契約に値条件が無い

**GraphQL は段階 4 である。** 型も関係判定も既にあるが、`graphql-core` の vendoring と
`parse()` が要るので、段階 3 では `match.body.graphql` を解禁しない。解禁するのは
`equals` と `oneOf` だけである。

## 決まっていること: 真偽を運び、値は運ばない

**broker はボディを持たない。** `broker.ts` の `toRequestBody` は
`{kind: "json", value: {}}` を捏造して `decide` に渡している。段階 2 まではそれで
足りていた。選択がボディの**形式**にしか依存せず、形式は `bodyKind` という 1 語で
運べたからである。値条件を入れた瞬間、broker の `decide` は addon と必ず割れる。

この設計は「addon と broker が同じドキュメントの上で同じ選択を再現し、ruleId が
食い違ったら fail-closed で止める」ことに依存している（`nas_addon.py` の
`AUTHZ-RULE-MISMATCH`）ので、割れたままにはできない。

**採る形: addon が候補ルールごとのボディ条件の真偽を送り、broker はそれを使う。**

- 運ぶのは (ルール ID → `"true" | "false" | "indeterminate"`) の対応表だけである。
  Pointer の値そのものは運ばない。
- **順序の判断は両側に残る。** broker は自分でスコープを選び、自分で候補を集め、
  自分で特異度と宣言順に並べ、自分で打ち切る。addon から受け取るのは
  「この候補のボディ条件は真か」という葉の述語だけである。選択規則の微妙な部分
  （「評価順」手順 3〜5）は 2 つの実装が独立に持ち続け、`decide_parity` が突き合わせる。
- 真偽は**そのルール自身の予算で評価した**真偽である（後述「予算の 2 段構え」）。

**`decide` の形。** 葉の述語を注入する。`decide` は順序と打ち切りだけを持ち、
「この候補のボディ条件は何か」を外から受け取る 1 つの関数（`rule => Truth`）に委ねる。

- broker は対応表を引く述語を渡す。ボディを持たないので他にできることがない。
- TypeScript の参照実装（テスト・パリティ試験）は `evaluateBody` を使う述語を渡す。
  値条件の意味論はここに 1 つだけ置く。
- addon は Python 側で同じ意味論を実装し、対応表を組み立てる。

こう分けないと、「真偽表から引く」と「`evaluateBody` に渡す」が `decide` の中で
二重に存在することになり、どちらが本物か決まらなくなる。

**電文で決めておくこと。**

- **候補は 1 つ残らず表に入れる。** ボディ条件を持たない候補（`match.body` が無い）も
  入れる。その真偽は常に真だが、**表に無いものは判定不能として扱う**ので、省くと
  条件の無いルールが判定不能に落ちて `onIndeterminate` が発火する。
- 欠落を判定不能に倒すのは、両者のドキュメントが食い違ったときの安全側である。
  `onIndeterminate` は `review` か `deny` しか取れないので `allow` には落ちない。
- 解決済みドキュメントに無いルール ID が表に現れたら**電文ごと拒否する**。broker は
  `documentHasRuleId` で同じ検査を既にしている。
- 件数の上限はスコープのルール数で足りる。検証器で閉じること。
- **`ReviewContext` には入れない。** `ReviewContext` は pending エントリに永続化され
  承認 UI へ渡る。真偽表は選択のための broker 内部の事実であって、人に見せるものでは
  ない。`AuthorizeRequest` の直下に置き、pending エントリ・監査ログ・UI のいずれにも
  写さない。
- `bodyKind` は選択に効かなくなるので `ReviewContext` から外す。誰も描画していない。

**採らなかった形と、その理由。**

- **Pointer の値を送る。** 値はボディ由来なので秘密を含みうる。マスクしてから送ると
  `equals` との比較結果が変わるので生で送るしかなく、ホスト側プロセスに秘密の経路が
  1 本増える。broker はそれを承認カードにも監査ログにも出さない運用を要求されるが、
  その不変条件を型で守る手段がない。得られるものは「broker が値を自分で比べられる」
  ことだけで、addon が値を偽れば選択が変わる点は真偽を送る場合と変わらない。
- **ボディそのものを送る。** 100KB の会話が毎リクエスト UDS を通る。上と同じ秘密の
  問題がさらに大きな形で来る。

**残る代償を書き留めておく。** ボディ条件という 1 軸について、broker の判定は addon の
答えに依存する。ruleId の突き合わせは残るので、ドキュメントの食い違い（メソッド・パス・
ターゲット・特異度）は今までどおり捕まる。捕まらなくなるのは「addon がボディ条件の
真偽について嘘をつく」場合だけであり、これは値を送る形でも同じである。

**電文の往復は増えない。** 対応表は既存の `authorize` に相乗りする。段階 2 で判明した
「addon の broker 問い合わせは 10 秒で諦める（mitmproxy の request フックが同期なので
伸ばすとプロキシ全体が止まる）」という制約は、段階 3 では悪化しない。

## やること

### 1. 葉の述語を注入する形にする（選択の帰結は変わらない）

値条件を入れる前に、**運び方だけ**を先に変える。

- `resolve.ts`: `decide` が葉の述語を引数で受け取る形にする。既定の述語は
  `evaluateBody` を使うもので、これが意味論の唯一の置き場になる。
- `protocol.ts`: `AuthorizeRequest` の直下に真偽表を足し、`ReviewContext.bodyKind` を
  外す。検証器を書くこと（上の「電文で決めておくこと」を満たすもの）。
- `broker.ts`: `toRequestBody` を捨て、対応表を引く述語を `decide` に渡す。
- `nas_addon.py`: 候補ごとの真偽を組み立てて `authorize` に載せる。

この時点では条件が `format` しかないので、**選択の帰結は今と同じになる**。既存の
統合テストがそのまま通ること。pending エントリから `bodyKind` が消えるのは想定内で、
UI は元から描画していない。

### 2. 値条件を解禁する（分割不能）

- `Schema.pkl`: `class BodyMatch` に `equals` / `oneOf` を足す。`graphql` は足さない。
- `authz/config.ts`: `BodyMatchConfig` を同じ形にする。
- `authz/resolve.ts`: 値条件を `ResolvedRule.match` に載せ、`evaluateBody` に本物を渡す。
- `nas_addon.py`: 契約の再検証（`_MATCH_KEYS` の拡張、Pointer と値の形の検査）と、
  `semantics.ts` と同じ 3 値評価の Python 実装。
- `AUTHZ_CONTRACT_VERSION` を 2 から 3 に上げる。

**このコミットは分割できない。** 契約のバージョンはホストと addon で完全一致を要求
する（`nas_addon.py` は `!=` で弾く）ので、片側だけ先に出すとその瞬間に全セッションが
403 になる。段階 1 のスキーマ変更と同じ性質である。

判定不能は仕様「判定不能」の 4 項目を網羅すること。特に **対象が存在しないのは偽で
あって判定不能ではない**。ここを混ぜると「壊れたボディを送れば条件を回避できる」抜け道
になる。

**候補ごとに適用する予算は `maxBodyBytes` だけである。** `maxDepth` / `maxNodes` は
検査の側の天井であり（仕様「予算」: 検査が始まる前に一度だけ検査する）、選択には
現れない。解析はスコープの予算で 1 度だけ行い、候補の `maxBodyBytes` がボディの
大きさに足りなければ、その候補にとっては解析できなかったボディ＝判定不能として扱う。
自分の予算より大きい数を宣言した候補にボディを解析し直してやることはしない。

**意味論のテストはこのコミットに含める。** パリティ試験は 2 実装の食い違いを見つける
道具であって、両方が同じように間違っていれば黙って通る。仕様から固定した期待値を
TypeScript と Python の**それぞれに**置くこと。最低限、次の 3 つは安全側の決定を
符号化しているので必ず固定する。

- Pointer の対象が存在しない → **偽**（判定不能ではない）
- 対象がスカラーでない → **判定不能**（偽ではない）
- 偽と判定不能が混じったら → **判定不能**が勝つ

### 3. 設定エラーを有効にする

- 受理集合の交差・包含判定に値条件を通す。`compileMatch` に渡すだけで、判定そのものは
  `relation.ts` に既にある。
- `format = "opaque"` **と `format = "none"`** に `equals` / `oneOf` を併記したら
  設定エラーにする。仕様「設定エラー」に 2 行並んでいる。散文の側（「ボディ条件」）は
  `opaque` にしか触れていないので、一覧の方を見ること。
- `equals` / `oneOf` の値が文字列・数値・真偽値のいずれかであることを検査する。Pkl の
  型は `Any` なので、オブジェクトや配列がここまで来る。
- キーが JSON Pointer の構文に従うことを検査する。**壊れた Pointer は静かに fail-open
  する。** 対象が見つからず条件が常に偽になり、そのルールはリクエストを引き受けず、
  より広いルールに拾われるからである。セレクタの `*` を弾いた話（`_is_valid_selector`）
  と同じ形の穴である。
- 空の `oneOf` を設定エラーにする。受理集合が空になり、その条件は決して満たされない。
  受理条件の側には同じ検査が `authz/validate.ts` にある（`expect.oneOf`）ので、`match`
  の側にも同じものを置く。

**設定エラーはホスト側で止める。** addon の契約検証だけに頼ると、セッションは起動して
しまい、最初のリクエストで 403 になる。`authz/validate.ts` で解決済みドキュメントを
作る前に落とすこと。このコミットのテストは設定を渡して診断が出ることを見る。

## 段階 2 から持ち越した、この段階で効いてくるもの

### 特異度順と宣言順のタイブレークが初めて効く

`resolve.ts` の `orderedCandidates` も `nas_addon.py` の `_order_candidates` も実装済み
だが、**段階 2 までは眠っている**。同じメソッドとパスを持ちボディの形式だけで分かれる
構成が存在しないので、候補は事実上 1 つに定まるからである。値条件を入れると候補が
複数になり、順序が答えを変える。

`decide_parity_test.ts` の設定にはこの日のために `ping.none` / `ping.json` が仕込んで
ある。`"json"` と `"none"` は互いを包含せず交差もしないので比較不能なまま設定エラーに
ならず、ボディ 0 バイトのリクエストで順序が観測できる。

### 予算の 2 段構えが値条件で壊れる

`_decide_under_rule_budget` は「まず選び、選んだルール自身の `maxBodyBytes` で
分類し直してもう一度選ぶ」という 2 段構えで、その docstring は **1 回の再実行が
不動点である**ことを次のように論証している。

> 予算超過が変えるのは `json` 条件を真から判定不能にすることだけであり、真も
> 判定不能も同じ候補で歩みを止めるので、2 回目は同じルールを名指しする。

**値条件を入れるとこの論証が成り立たない。** `equals` は予算超過で**偽から判定不能**へ
変わりうる。偽は歩みを進め、判定不能は歩みを止めるので、2 回目がより手前の候補で
止まり、別のルールを名指しする。

案 b の真偽表はこれを構造的に解く。**各候補の真偽をその候補自身の予算で評価して
表に入れれば、歩みは 1 パスで済み、2 段構えそのものが要らなくなる。** 段階 3 は
`_decide_under_rule_budget` を削り、その docstring が守っていた性質を真偽表の側の
不変条件として書き直す段階でもある。

### パリティ試験の直積が足りなくなる

`decide_parity.py` は `(host, port, method, path, body_kind)` の直積を流している。
`body_kind` は 4 語しかないので、値条件のある選択を突けない。**実ボディを流す形に
変えること。** 打ち切りの順序が観測できる組（上記 `ping.none` / `ping.json`）を必ず
入れること。両実装が同じように間違うのがこの試験の想定する危険であり、片側だけ
正しい実装は「静かな緩み」ではなく「動かないセッション」になる。

`message_parity_test.ts`（段階 2 で追加）は電文の形を突き合わせる別の試験である。
真偽表を足したら、こちらにも 1 件足すこと。

### 予算の節に戻る必要はない

仕様「予算 > 既定値どうしの関係（実測）」は「受理条件を 1 本足すと `maxNodes`
ぎりぎりの正常なボディが `resource-limit` の 403 になる」と警告しているが、**値条件は
この計算に入らない**。`equals` のキーは `*` も `**` も持たない完全な JSON Pointer で
あり、走査ではなく直接参照だからである。`maxSelectorExpansions` を消費しない。

段階 3 は受理条件を増やす段階ではない。preset にも手を入れない。

### `hostexec.secrets` が未統合

仕様は秘密のレジストリを 1 つに統合すると言っているが、`hostexec.secrets` は
プロファイル直下の `secrets` と二重に存在したままである。段階 3 の作業ではないが、
**判断が要る宙ぶらりんの項目として残っている**。

### 段階 2 のレビューが残した 1 件

`src/hostexec/secret_store.ts` の `runSecretCommand` が `child.stdout` を読み切って
から `child.stderr` に触るので、ヘルパーが stderr にパイプバッファを超えて書くと
デッドロックし、セッション起動が無限に止まる。段階 1 由来で、段階 3 とは無関係だが
未修正である。`Promise.all` で両方同時に読むだけで直る。

## 完了の条件

- `match.body` に `equals` / `oneOf` を書いた設定で、値の違いによって別のルールが
  選ばれる
