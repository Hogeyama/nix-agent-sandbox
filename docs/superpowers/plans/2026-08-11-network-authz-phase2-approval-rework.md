## 仕様の「段階 2」のうち、すでに終わっているもの

仕様「実装の段階 > 段階 2」は 4 項目を挙げているが、**下の 2 つは段階 1 で先に入った**。
仕様の側を読むときに二度手間にならないよう先に書いておく。

- **`pendingDefaultScope` の削除と、承認粒度をルールの具体性から導出すること** — 済み。
  ただし後述の制限つき
- **`$fallback` 擬似 ID** — 済み

残るのは次の 2 つで、これが段階 2 の本体である。

- 違反の所見を broker に渡す
- 承認の単位を (ルール ID, 受理条件の識別子, 違反した値) にする

## やること

### 1. 所見を addon の外に出す

**現状、所見は addon の中で消える。** `_inspect_body` は違反ごとに所見（受理条件の名前、
JSON Pointer、見つかった値、そのノードの抜粋、同種の件数）を組み立てているが、使い道は
`_findings_block_reason` が帰結を 1 つ選ぶことだけである。broker に送る
`request_policy_outcome` は requestId / sessionId / ruleId / result / reason の閉じた
集合しか運ばない（`src/network/protocol.ts`）。

所見を broker まで運ぶ。プロトコルの拡張が要る。

### 2. 承認の単位を変える

現状は **(ルール ID, 判定理由, ターゲット)**。段階 2 では、受理条件の違反から生じる
承認を **(ルール ID, 受理条件の識別子, 違反した値)** で識別する。broker が承認済みの
集合を保持する。

**これが段階 2 の実運用上の利得である。** 会話履歴を再送するたびに同じ未知タグで同じ
確認が繰り返される問題が、これで解ける。

`onMatch = "review"` から生じる承認（段階 1 で作ったもの）とは**別の同一性**である。
2 種類の承認が同じ broker に共存する形になる。どちらの鍵でも引けるようにするのか、
種別を持たせるのかは実装の判断だが、**一方の承認が他方を解放してはならない**。

### 3. `onViolation = "review"` を解禁する

段階 1 では `deny` と `allow` だけだった。preset の `onViolation` を `review` に
切り替えるのもこの段階である。

### 4. `bodyPreview` を所見に置き換える

現行の `bodyPreview` は先頭 1024 バイト（`nas_addon.py` が組み立て、
`mask_patterns.ts` がマスクする）。`/v1/messages` の実トラフィックは 100KB を超えるので、
承認者は違反箇所を見ないまま押すことになる。所見はセレクタ走査中に確定しているので、
そちらに置き換える。

## 段階 1 から持ち越した、この段階で効いてくるもの

**段階 1 では観測不能だったものが、所見を外に出した瞬間に観測可能になる。** ここに
挙げたものは全部「今は誰も見ていないから問題にならない」で通してきたものである。

### 所見の保持上限が承認を作れなくする

`MAX_RETAINED_FINDINGS = 64`。上限に達したあとの違反は**件数だけ数えて、受理条件の
名前も JSON Pointer も違反した値も保持しない**。しかも上限はリクエストのボディ検査
**全体で共有**なので、先行する受理条件が上限を埋めると後続の受理条件の違反が丸ごと
畳まれる。

承認の単位が (ルール ID, 受理条件の識別子, 違反した値) である以上、**畳まれた違反は
承認できない**。段階 1 ではこれが問題にならなかった（`onViolation` に `review` が
無いため）。**段階 2 では正面から当たる。**

上限そのものは要る（攻撃者が選ぶタグ文字列がグループ化キーなので、上限が無いと
1.9MiB のボディで 99,000 件の所見が出る）。受理条件ごとに配分するのか、承認に必要な
最小限（識別子と値）だけ上限の外に出すのかを決めること。

### 抜粋の各種上限が UI に出る

`EXCERPT_MAX_DEPTH = 3` / `EXCERPT_MAX_BYTES = 512` / `EXCERPT_MAX_WIDTH = 16` /
`EXCERPT_MASK_BUDGET = 4096`。いずれも実装者が決めた値で、仕様は「深さとバイト数で
打ち切る」としか言っていない。承認 UI が実際に描画するようになってから、承認者が
判断できる情報量になっているかを見直すこと。

抜粋の中で**マスクされたオブジェクトキーが衝突すると後勝ちになる**。段階 1 では表示
専用の成果物なので許容した。UI に出るなら再検討の対象になる。

### 所見に生の秘密を載せない

**段階 1 でこの不変条件を 2 回破っている。** 抜粋が JSON エスケープの後にマスクされて
いて引用符・バックスラッシュ・改行を含む秘密が素通りしたのが 1 回、JSON Pointer が
そもそもマスクされていなかったのが 1 回。どちらも承認 UI と監査ログに流れる経路だった。

承認 UI は所見の**新しい消費者**である。値・抜粋・Pointer のどのフィールドにも生の
秘密が載っていないことを、経路が増えるたびに確かめること。

### 予算に余裕がない

受理条件を 1 本足すと、`maxNodes` ぎりぎりの**正常な**ボディが `resource-limit` の
403 になる。仕様「予算 > 既定値どうしの関係（実測）」に数字がある。段階 2 は受理条件を
増やす段階ではないが、`review` を解禁すると preset に受理条件を足したくなる。**足す前に
その節を読むこと。**

### `rule` 粒度の提示条件が仕様より狭い

段階 1 は `rule` 粒度を「単一の exact な host:port を持つスコープ」にだけ提示している。
1 回の承認が承認者の見ていないターゲットを覆わないための、安全側への判断である。
仕様の文はもっと広く読める。段階 2 で承認の種類が増えるので、ここで統一的に決め直す
機会になる。

### `hostexec.secrets` が未統合

仕様は秘密のレジストリを 1 つに統合すると言っているが、`hostexec.secrets` は削除対象
にも段階 1 の作業にも入っていなかった。プロファイル直下の `secrets` と二重に存在して
いる。段階 2 の作業ではないが、**判断が要る宙ぶらりんの項目として残っている**。

## コミットの割り方（案）

段階 1 と違い、**分割不能なコミットは無い**。スキーマの破壊的変更を伴わないため。

| | 内容 | 既存挙動 |
| --- | --- | --- |
| T1 | 所見の保持を承認可能な形にする（上限の配分） | 変わらない（所見はまだ外に出ない） |
| T2 | 所見をプロトコルに載せて broker まで運ぶ | 変わらない（broker はまだ使わない） |
| T3 | 承認の単位に (受理条件, 違反した値) を足す。承認済み集合の保持 | 変わる |
| T4 | `onViolation = "review"` を解禁。`bodyPreview` を所見に置き換える | 変わる |
| T5 | preset の `onViolation` を `review` に切り替える | 変わる |

T1 が先頭なのは順序の要請である。**上限の配分を直す前に所見を外に出すと、承認できない
違反が UI に出る。**
