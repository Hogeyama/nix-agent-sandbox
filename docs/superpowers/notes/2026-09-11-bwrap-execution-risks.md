# bwrap の実装を Codex に任せる前の懸念

> 後続の検討で前提を見直し、[NixOS ホストでの Testcontainers 実証](2026-09-11-bwrap-testcontainers-feasibility.md)が進んだ。以下は旧 rootfs 配布案を対象とした懸念の記録であり、全項目が現在も未着手という意味ではない。

対象: [spec](../specs/2026-09-11-bwrap-backend-design.md) と [plan](../plans/2026-09-11-bwrap-backend.md)。確認時の worktree HEAD は `bf09ccb1`。
Status: 懸念と運用案の整理。プロダクト実装は開始していない。以下の試行・承認単位は提案であり、全工程の実行承認を意味しない。

## 判断

現時点で約 40 コミットを一括実行する準備は足りない。最初の小さい実証・実装・レビュー・再開を一巡させてから、後続をまとまった単位で任せる案を推す。

32–45 コミットは責務分割から出した概算であり、所要時間、費用、成功確率の見積りではない。
前回の subagent レビューは設計上の重大矛盾を調べたもので、長期実行を完走できるという保証ではない。今回は新規のレビュアーにも、実行・中断・レビューの運用だけを点検してもらった。

## 着手前に解消する懸念

### 1. 最重要の試験を現在の環境で実行できない

コンテナ内の namespace 作成は既に拒否されている。unit の 3475 pass / 9 skip は baseline として有用だが、bwrap の隔離、FUSE、PTY、seccomp、owner 死亡時の回収を実証していない。
plan は Ubuntu 24.04/NixOS の試験を要求するが、使うホスト・担当・到達経路が未確定。コードだけ増えて合否を判断できない状態が最も懸念される。

開始条件として、対象ホスト、実行役（ユーザーまたは利用可能な runner）、非 secret fixture の配置、実行・ログ回収方法を決める。
ログは `commit / runtime digest / host条件 / command / exit code / pass・skip・fail` を対応づける。agent の「通った」という要約だけを証拠にしない。
ホストへの権限変更や sandbox の緩和を失敗時の自動処理に含めない。

### 2. 全体方針の未承認事項が実装判断に紛れ込む

Nix 不要・ライセンス配慮はユーザーの必須条件。対して agent 内 devShell の初期非対応、配布 rootfs の継続保守、guardian 方式、owner 死亡時の終了契約は提案中である。
これらを subagent の裁量で既定の決定として扱うと、実装後に目的とのずれが発覚する。

開始前に必須条件と採用案を区別した決定表を置く。必須条件は各 brief に明記し、提案は承認状況を記録する。
「Nix なしでも使える」を「Nix 利用の互換性を捨ててよい」という承認に読み替えない。

### 3. task brief の作成はまだ実行準備として残っている

plan は既に大項目の分割を要求しているので、「10項目しかないから不可能」という問題ではない。
ただし実際の小さい brief は未作成。helper `task-brief` を Task 7 に対して実行すると、supervisor・guardian 全体の 21 行を抽出した。グローバル制約や小タスクへの分割は自動で補われない。

最初の大項目だけ、1 回の実装・レビューで受け入れられる単位に分割する。各 brief に変更目的、入出力、依存、変更対象、受入試験、禁止する変更、失敗時の扱いを含める。
全 40 件を最初から詳細化する必要はないが、後続の共有 interface を各担当が独自に定義しないよう、protocol/identity/error の契約は先に固定する。

Task 7 の PTY・親死亡・host 子孫回収は不確実性が大きい。配布機構を作り込む前に、その最小動作を独立 probe として先行確認する余地がある。現 plan の順序変更はこの検証範囲を決めてから反映する。

## 長期実行で故障しやすい箇所と対策案

| 懸念 | この作業での具体的な失敗 | 対策案 |
| --- | --- | --- |
| 再開時の状態取り違え | commit 済み・review 未完了を「未着手」と見て重複実装する | 完了行だけでなく途中状態、BASE/HEAD、担当、証拠、次の操作を記録し Git と照合する。 |
| 共通制約が文脈から抜ける | 古い Nix 必須案、host network、dtach のコード利用を復活させる | brief へ必須条件を含める。最新決定表の版を指定し、会話の記憶だけに依存しない。 |
| reviewer の合格を過大解釈 | rule 違反がないことを全要件完了と数える | 受入条件ごとの「充足・未充足・未検証」と証拠を controller が確認する。 |
| 同じ前提の見落とし | 実装者と reviewer が同じ不正確な plan に従って合意する | reviewer に実装者の結論を答えとして渡さない。重要境界は負例・障害注入と実機結果で判定する。 |
| 共有 worktree の競合 | fixer の編集中に親が commit、別担当が同ファイルを書き換える | 編集・git操作は同時に一名。review 対象 HEAD を固定し、変更後は再レビューする。 |
| 着手後の main との乖離 | 着手前 rebase 後にも main が進み、最終統合で古い mask/IPC 前提が残る | 着手前 rebase はユーザーの方針として確定。長期作業中は節目で差分を確認し、必要な取り込み後に影響範囲を再検証する。 |
| レビューが最後に集中 | 40 コミットを一度に見せられ、契約違反を見抜けない | 各小タスクは自動レビューし、人間レビューは意味のある中間成果でまとめる。 |
| コストと再試行の増大 | 同じ host 制約で試行を繰り返し、配布/ライセンス調査が膨張する | 最初の試行で時間・再試行・利用量を計測する。同じ原因が続く場合は証拠を整理して方針へ戻る。 |
| 進捗率が実用性を表さない | helper と型は完成しても agent が起動しない | コミット数に加えて、実行できるシナリオと未検証境界を報告する。 |

公式の [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) も、大量の中間出力による文脈の劣化、並列編集の競合、subagent による利用トークン増加を説明している。
この環境の subagent は同じ filesystem を共有するため、別会話であることを別 worktree であることと混同しない。並列化はまず調査・読み取りレビューに限定する。

## 既存ワークフローで足りている点・足りない点

`subagent-driven-development` には新規 implementer、タスクごとのレビュー、完了 ledger、並列 implementer 禁止がある。
`patched-superpowers` には全体レビューと人間レビューもある。そのため、これらが全く無いという評価ではない。

不足するのは、途中停止の状態、要件別の充足判定、実際の host test 経路、今回の tool で全体レビューを実行する手順の実証である。
独自 reviewer の `passed` は規約の `stop_when` に基づく。これを使う場合も、受入条件の未検証を別に表示し、コードレビュー合格だけで host gate を完了にしない。

CLI の `diffity`、`forgejo` と wrapper、brief/review-package helper は存在する。ただし存在確認は、全工程のレビュー・コメント回収・再開を完走した証拠ではない。
小さい試行で現在の Codex tools による dispatch → review → 修正 → 証拠回収を確認する。スキルの slash command 名を、そのまま実行可能な tool と仮定しない。

確認時点で main は検討基準 `6b152b9b` から 10 コミット進み、`6d9f7f2d` にある。ユーザーは実装着手前にリベースする方針を明示した。この文書作成ではリベースを実行していない。
着手前リベース後に baseline を再取得し、最初の実装前の HEAD を `implementation-base` に記録する。先の 3475 pass は旧基準の結果なので、そのまま新基準の合格証拠にしない。これで着手時の乖離は解消できる。
着手後にも main を取り込む場合は、そのコミットと回帰確認を別に記録する。全体レビューに無関係な upstream 差分を混ぜないよう範囲を管理する。

## 再開に必要な記録の最小形

以下は提案する記録項目。まだ実装状態として記入していない。

| 項目 | 保存するもの |
| --- | --- |
| 対象 | worktree 絶対パス、branch、承認済み spec/plan の版 |
| 作業単位 | 安定した subtask ID、brief、依存タスク |
| 状態 | 未着手 / 実装中 / 検証中 / レビュー中 / 修正中 / 完了 / 外部条件待ち |
| Git | 開始 BASE、最後に確認した HEAD、途中 commit、未コミット変更の有無 |
| 判定 | テストの実行環境・結果・ログ、未解決 finding、未検証の受入条件 |
| 再開 | 次に行う一つの操作、実行中の担当と job、次の停止条件 |

再開時は記録と `git status`/`git log` を照合する。未コミット差分があればまず由来を確認し、リセットや再 dispatch で上書きしない。
review 中に停止した場合は、実装を繰り返さず記録した diff 範囲のレビューから再開する。
短期ログは一時領域に置けるが、再開に必要な決定・commit・判定はそれだけに依存せず、リポジトリ内の進捗記録へ要約する。秘密を含むログは記録対象から除外する。

公式の [長時間タスク向け計画ガイド](https://developers.openai.com/cookbook/articles/codex_exec_plans) は、計画・進捗・判断を更新し、そこから再開できる形を示している。この作業でも、引継ぎ情報だけで次の担当が続行できることを試行で確かめる。

## 最初の試行と、その後へ進む条件の提案

最初はホスト検証経路と最初の brief を整え、初期 probe の小さい一単位を実装・検証・レビューする。
安全なタスク境界で一度引き継ぎ、最新 brief・進捗記録・Git だけを受け取った新規担当が次の操作を正しく判断できるか確認する。破壊的な停止試験で Codex 自身を落とす必要はない。

その試行で次を満たせば、まとまった後続作業を任せる判断材料になる。

1. host 結果を commit/runtime digest と対応づけて取得できた。
2. 必須条件を失わず、一つの変更をレビュー可能なサイズに収められた。
3. 中断・引継ぎで完了済みの作業を再実行せず、未解決 finding から再開できた。
4. 要件別の未検証が見える状態で、時間・再試行・レビュー負担を報告できた。

この試行の成功は全工程の成功保証ではないが、今の「文書上はできそう」より判断材料が増える。
日常的な小タスクごとの確認要求を増やす案ではなく、最初の試行と major milestone で任せる範囲を区切る提案である。
