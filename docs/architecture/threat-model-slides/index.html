GitHubではREST/GraphQLとGitの取得・更新を使う。必要な接続先はapi.anthropic.com、github.com、api.github.com、devapi.example.com。指定repoの投稿者が提供する内容を信頼済みとするため、外部投稿者や未審査の内容を取り込むなら前提を見直す。業務APIはx-api-keyだけで認証し、重複headerを拒否する。他のheader・query・bodyによる認証や認証主体の切替はなく、有効なkeyは自組織の開発環境だけにアクセスできる仮定。auto modeはmanaged settingsで全shellコマンドを審査し、取得元制限の自然言語ルールも設定する。WebSearchの結果はAnthropic APIの応答となるため、proxyでは取得元を判定できない。全条件と各構成の設定は設定例を参照。[Sources] ../threat-model.md「比較の共通条件」 ../threat-model-configurations.md「共通設定」 [/Sources]

この例では、社内のrepoへの書込みだけを許可したい。利用者のtokenは社内のrepoへ、攻撃者が持ち込むtokenは攻撃者のrepoへ書き込めるものとする。通信制限は宛先がapi.github.comかだけを調べるため、どちらの要求も通す。GitHub側では各tokenの権限に従って書込みを許可する。利用者のtokenの権限を絞っても、攻撃者のtokenを使う操作にはその制限が適用されない。未許可サービスへの送信がA1a、許可サービス内の未許可相手への送信がA1b。表は有効tokenによる流出の実測結果を表してはいない。[Sources] ../threat-model.md「被害と必要な防御」「通信先・権限・信頼済み情報源」 [/Sources]

Docker Sandboxの認証処理

実測対象はv0.45。GitHubのアカウント情報を取得するAPIに、同じ無効なtokenを送った。

通常のproxyは、送信時にtokenをホストに保存した認証情報へ置き換える。

経路観測した応答
通常のproxy経由200成功。ホスト側のアカウント情報が返った
認証proxyを使わない経路401 Bad credentials。通信は届き、GitHubが無効なtokenを拒否した

proxyを使わない経路では、証明書とログでも認証情報の置換を通らないことを確認した。

コーディングエージェントのセキュリティ対策8 / 18

Linux上のsbx v0.45、GitHub GET /userで測定。直接接続にはcurl --noproxy '*'を使った。通常経路はDockerのCAとforwardログ、直接経路はGitHubの公開証明書とtransparentログだった。認証headerなしの通常経路でも200となる正常系を先に確認した。通信部分の実験であり、比較設定の全再現ではない。workspace mountなしで、clone modeは使っていない。有効な攻撃者tokenによる第三者repoへの書込み・git push・Anthropic Files APIは未検証。[Sources] ../experiments/sbx-a1b/README.md「構成と正常系の対照」「観測結果」 [/Sources]

Docker Sandboxの評価

接続先のホスト名を制限し、proxyで認証情報を置き換える構成を評価する。

  1. 仮定：攻撃者は、自分のrepoに書き込めるtokenを持ち込める。
  2. 実測：プログラムが指定したtokenを、置き換えずにGitHubへ送れる経路があった。
  3. 判断：その経路で有効なtokenを使われると、書込み先のrepoを制限できないと評価する。未許可repoへの流出を阻止する要求は満たさない。
  4. 未検証：有効な攻撃者tokenでの書込みと、情報流出の完遂。
コーディングエージェントのセキュリティ対策9 / 18

経路の成立を観測し、攻撃者が有効なcredentialを持つ脅威モデルに照らして判断した。○は「安全」という意味ではなく、今回求めた◎に未達であることを表す。通常の認証注入や共通の操作審査は過失低減として評価する。v3 kitのHTTP制限を使う構成は未実測で、この判定には含めない。[Sources] ../experiments/sbx-a1b/README.md「判定と実測の限界」 ../threat-model.md「系統5: Docker Sandbox」 [/Sources]

構成比較に用いた設定制限を評価する根拠
内蔵sandboxBashを隔離。WebFetch・MCP・隔離外での実行を無効化設定：Claude Code本体のホスト書込みを、一律には禁止していない

内蔵sandbox・srt・Dev Container・nasの保護範囲は提示設定と仕様に基づく。srt 0.0.77ではSOCKS経由でTLS終端を通らず許可ホストへ届いたため、filterRequestを実装しても認証・repo検査は強制できないと判断する。実測は偽tokenへの認証エラーまで。Dev ContainerではDNS resolverを限定しても外部への問合せが転送されるため情報を送れる。IPで許可するため、共有IP上の別hostnameも区別しない。Docker Sandboxはclone modeでホストrepoをread-only mountし、shared skillsとSSH agent forwardingも無効にする。通信の実測は名前とIPを食い違わせた試行であり、すべての接続方式を検証したものではない。nasはGitHubに加え、AnthropicのFiles APIを拒否し、業務APIには共通条件の限定仕様を仮定する。[Sources] ../threat-model.md「各方式の評価理由と成立条件」 ../experiments/srt-filter-bypass/README.md ../experiments/sbx-shared-ip/README.md [/Sources]
