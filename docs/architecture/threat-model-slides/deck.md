# コーディングエージェントのセキュリティ対策

<!-- notes: Claude Codeに開発作業を任せる際の権限と制限を整理し、5つの実行環境を比較する。[Sources] ../threat-model.md [/Sources] -->

## 目的と構成

Claude Codeを動かす5つの構成について、どの被害を防げるか、どの設定が必要かを比較する。

1. 仮定：攻撃者に可能な操作と、信頼する仕組み
2. 要求：防ぎたい被害と、求める防御の強さ
3. 仕様・実測：各構成が設ける制限と、実験で確認した挙動
4. 評価：その制限が、想定した攻撃を止められるか

<!-- notes: 対象はClaude Codeを開発に使う人。防御の要求水準は選んだ方針、仕様や実測はその方針への適合を判断する材料として区別する。比較表の記号は測定結果そのものではない。[Sources] ../threat-model.md「脅威モデルと要求水準の決め方」「比較結果と構成ごとの条件」 [/Sources] -->

## 想定する誤操作と攻撃

エージェントと、その実行するプログラムについて、次の動作を仮定する。

| 種類 | 動作の例 |
| --- | --- |
| 誤操作 | 利用者の指示に従おうとして、削除対象のパスを間違える |
| 攻撃 | 悪意ある指示やプログラムにより、攻撃者のtokenで情報を送る。制限の回避も試みる |

隔離機構、制限を設定する管理者側の仕組み、承認システム自体への侵害は、この比較の対象外とする。

<!-- notes: 攻撃はエージェントの判断を介さず、隔離環境内のプログラムが直接行う場合も含む。制約回避やプロンプトインジェクション、侵害されたMCP server等を想定する。信頼する対象の選択は脅威モデルの前提であり、攻撃の起こりやすさや隔離機構の無欠陥を実測した結果ではない。[Sources] ../threat-model.md「敵対的な操作と過失を分ける」 [/Sources] -->

## 防ぎたい被害と要求水準

この比較では、開発に必要な編集や通信を許可し、次の防御を要求する。

| 被害 | 求める防御 |
| --- | --- |
| 許可していない相手への情報流出 | 攻撃でも阻止する |
| 編集を許可しないホストファイル・既存設定の変更 | 攻撃でも阻止する。作業フォルダ内のホスト用.git/configやhookも対象 |
| 本番の変更、公開、権限の変更 | 攻撃でも阻止する |
| 編集を許可したソース・履歴・記憶データの破壊や改変 | 誤操作による被害を減らす。悪意ある変更は残るリスクとして扱う |
| 許可した相手への秘密の誤送信、ファイルへの誤保存 | 誤操作による被害を減らす |

<!-- notes: この水準は今回選んだ方針であり、すべての用途に共通する必須条件という主張ではない。任せた範囲を越える影響は阻止し、編集を許した内容は審査と復旧を組み合わせる。ホスト設定は復旧可能でも保護する。作業領域内の既存.git/configやhookとその参照先も、ホストで使うものは保護対象。新しく作った設定は作業成果物として採用前にレビューする。履歴やmemoryを次の実行で再利用すれば、改変の影響も引き継ぐ。[Sources] ../threat-model.md「被害ごとに求める防御の水準」「ホスト・作業領域・履歴への被害の違い」 [/Sources] -->

## 比較条件

許可方針と設定を以下のように定め、方針に反する操作を止められるかを評価する。

| 区分 | 比較に使う方針・設定・仮定 |
| --- | --- |
| 許可方針 | 通信先はAnthropic API、GitHub、開発用の業務APIに限る |
| 許可方針 | GitHubで読み書きしてよいのは、自組織の指定した非公開repoだけ |
| 設定 | 利用者のtokenの権限を必要最小限にする。本番の認証情報は渡さず、CIの権限と承認設定も制限する |
| 設定 | Claude Codeが実行しようとするshellコマンドをauto modeのAIが審査する。WebSearchツールは外す |
| APIの仮定 | 業務APIは自組織の開発環境専用で、第三者への保存・転送機能がない架空のAPIとする |

AIの操作審査は、誤操作による被害を減らす対策として評価する。

<!-- notes: GitHubではREST/GraphQLとGitの取得・更新を使う。必要な接続先はapi.anthropic.com、github.com、api.github.com、devapi.example.com。指定repoの投稿者が提供する内容を信頼済みとするため、外部投稿者や未審査の内容を取り込むなら前提を見直す。業務APIはx-api-keyだけで認証し、重複headerを拒否する。他のheader・query・bodyによる認証や認証主体の切替はなく、有効なkeyは自組織の開発環境だけにアクセスできる仮定。auto modeはmanaged settingsで全shellコマンドを審査し、取得元制限の自然言語ルールも設定する。WebSearchの結果はAnthropic APIの応答となるため、proxyでは取得元を判定できない。全条件と各構成の設定は設定例を参照。[Sources] ../threat-model.md「比較の共通条件」 ../threat-model-configurations.md「共通設定」 [/Sources] -->

## GitHubの接続許可と書込み先

社内repoにだけ情報を渡したい場合の例。通信制限ではapi.github.comへの接続を許可し、tokenやrepoは検査しない。

エージェント内のプログラムが、次のtokenを使えると仮定する。

| 書込み先 | 接続先のホスト名 | 使えるtoken | 通信の可否 |
| --- | --- | --- | --- |
| 社内のrepo | api.github.com | 社内repoへの書込み権限を持つ利用者のtoken | 通る |
| 攻撃者のrepo | api.github.com | そのrepoへの書込み権限を持つ、攻撃者が持ち込んだtoken | 通る |

<!-- notes: この例では、社内のrepoへの書込みだけを許可したい。利用者のtokenは社内のrepoへ、攻撃者が持ち込むtokenは攻撃者のrepoへ書き込めるものとする。通信制限は宛先がapi.github.comかだけを調べるため、どちらの要求も通す。GitHub側では各tokenの権限に従って書込みを許可する。利用者のtokenの権限を絞っても、攻撃者のtokenを使う操作にはその制限が適用されない。未許可サービスへの送信がA1a、許可サービス内の未許可相手への送信がA1b。表は有効tokenによる流出の実測結果を表してはいない。[Sources] ../threat-model.md「被害と必要な防御」「通信先・権限・信頼済み情報源」 [/Sources] -->

## Docker Sandboxの認証処理

実測対象はv0.43.0。GitHubのアカウント情報を取得するAPIに、同じ無効なtokenを送った。

通常のproxyは、送信時にtokenをホストに保存した認証情報へ置き換える。

| 経路 | 観測した応答 |
| --- | --- |
| 通常のproxy経由 | 200成功。ホスト側のアカウント情報が返った |
| 認証proxyを使わない経路 | 401 Bad credentials。通信は届き、GitHubが無効なtokenを拒否した |

proxyを使わない経路では、証明書とログでも認証情報の置換を通らないことを確認した。

<!-- notes: Linux上のsbx v0.43.0、GitHub GET /userで測定。直接接続にはcurl --noproxy '*'を使った。通常経路はDockerのCAとforwardログ、直接経路はGitHubの公開証明書とtransparentログだった。認証headerなしの通常経路でも200となる正常系を先に確認した。通信部分の実験であり、比較設定の全再現ではない。workspace mountなしで、clone modeは使っていない。有効な攻撃者tokenによる第三者repoへの書込み・git push・Anthropic Files APIは未検証。[Sources] ../experiments/sbx-a1b/README.md「構成と正常系の対照」「観測結果」 [/Sources] -->

## Docker Sandboxの評価

接続先のホスト名を制限し、proxyで認証情報を置き換える構成を評価する。

1. **仮定**：攻撃者は、自分のrepoに書き込めるtokenを持ち込める。
2. **実測**：プログラムが指定したtokenを、置き換えずにGitHubへ送れる経路があった。
3. **判断**：その経路で有効なtokenを使われると、書込み先のrepoを制限できないと評価する。未許可repoへの流出を阻止する要求は満たさない。
4. **未検証**：有効な攻撃者tokenでの書込みと、情報流出の完遂。

<!-- notes: 経路の成立を観測し、攻撃者が有効なcredentialを持つ脅威モデルに照らして判断した。○は「安全」という意味ではなく、今回求めた◎に未達であることを表す。通常の認証注入や共通の操作審査は過失低減として評価する。v3 kitのHTTP制限を使う構成は未実測で、この判定には含めない。[Sources] ../experiments/sbx-a1b/README.md「判定と実測の限界」 ../threat-model.md「系統5: Docker Sandbox」 [/Sources] -->

## 各構成の保護設定

| 構成 | 比較に用いた設定 | 制限を評価する根拠 |
| --- | --- | --- |
| 内蔵sandbox | Bashを隔離。WebFetch・MCP・隔離外での実行を無効化 | 設定：Claude Code本体のホスト書込みを、一律には禁止していない |
| srt | Claude Code全体の書込みを制限。Git設定・hook・.claudeを保護 | 実測：0.0.77で、認証情報を置き換えずに許可先へ送れる経路を確認 |
| Dev Container | コンテナ内で接続先IPを制限。作業フォルダをホストと共有 | 仕様・設定：DNSで情報を送れ、同じIP上の別ホスト名にも接続可能。共有する設定は書換え可能 |
| nas | GitHubのtoken・repo・操作をproxyで制限。AnthropicのFiles APIは拒否 | 仕様：範囲外は承認まで停止。業務APIは、比較条件の架空の仕様を前提とする |
| Docker Sandbox | ホストrepoは読取り専用。VM内のコピーを編集 | 実測：ホスト名による通信制限と、認証情報の置換を通らない経路を確認 |

<!-- notes: 内蔵sandbox・srt・Dev Container・nasの保護範囲は提示設定と仕様に基づく。srt 0.0.77ではSOCKS経由でTLS終端を通らず許可ホストへ届いたため、filterRequestを実装しても認証・repo検査は強制できないと判断する。実測は偽tokenへの認証エラーまで。Dev ContainerではDNS resolverを限定しても外部への問合せが転送されるため情報を送れる。IPで許可するため、共有IP上の別hostnameも区別しない。Docker Sandboxはclone modeでホストrepoをread-only mountし、shared skillsとSSH agent forwardingも無効にする。通信の実測は名前とIPを食い違わせた試行であり、すべての接続方式を検証したものではない。nasはGitHubに加え、AnthropicのFiles APIを拒否し、業務APIには共通条件の限定仕様を仮定する。[Sources] ../threat-model.md「各方式の評価理由と成立条件」 ../experiments/srt-filter-bypass/README.md ../experiments/sbx-shared-ip/README.md [/Sources] -->

## 比較評価

仕様・設定と一部の実測に基づく評価。全項目を実測した表ではない。

◎ 攻撃による操作も、拒否または人間の承認待ちで止める。

○ 誤操作による被害を減らす。攻撃では回避される場合がある。

| 防御対象・要求水準は◎ | 内蔵sandbox | srt | Dev Container | nas | Docker Sandbox |

| 編集を許可しないホストファイル・既存設定の変更 | ○ | ◎ | ○ | ◎※ | ◎ |

※ nasは、既存設定とhookを保護する配置・設定が条件。

<!-- notes: 評価根拠は方式別の仕様・設定と個別実験であり、全セルを実測したものではない。内蔵sandboxは本体のホスト書込み制限が不足。srtは全プロセスと既存設定を保護する一方、0.0.77ではSOCKS等による要求検査の迂回を観測。Dev ContainerはDNS問合せや共有IPによる通信、共有作業領域内の既存設定への書込みが残る。nasはproxyを経由させ、共有先・操作を検査する。Docker Sandboxはv0.45.1で名前とIPを食い違わせた接続の判定を観測し、未許可の名前への接続が拒否された。実際に同一IPを共有する組合せや全プロトコルを網羅してはいない。ホスト保護はclone mode等の設定による評価。◎には、保護された人間承認が届くまで必ず操作を止める構成も含む。B1はCI等に共通の導入条件として求め、方式間では採点しない。[Sources] ../threat-model.md「被害防止と予防の比較」「各方式の評価理由と成立条件」 ../experiments/sbx-shared-ip/README.md「判定と実測の限界」 [/Sources] -->

## nasの利用条件

| 対象 | 利用条件と残るリスク |
| --- | --- |
| GitHub | proxyがrepo・操作を検査し、tokenを利用者のものへ置換。範囲外は人間の承認まで止める |
| Anthropic・業務API | Anthropicのファイル保存APIは拒否。業務APIは、自組織の開発環境だけにアクセスできる仕様を仮定 |
| ホストの設定 | 既存設定・hook・参照先と、作業フォルダの.claudeを保護する |
| 作業内容・履歴 | エージェントが書換え可能。履歴・記憶データはホストと共有し、次の実行で再利用する |
| 運用 | 利用者がAPIごとの許可設定を保守する。承認者の判断精度や確認負担は未実測 |

<!-- notes: nasではコンテナ外のproxyがGitHubのrepo・操作・GraphQL本文を検査し、範囲外は承認待ちにする。利用者の認証情報へ上書きし、AnthropicのFiles APIは拒否する。業務APIは比較条件の限定された仕様を仮定。既存設定やhookの参照先も保護対象に収め、作業領域の.claudeを追加設定で保護する。履歴やmemoryはホストと共有し、次の実行へ内容の改変も引き継ぐ。承認の負担や審査精度は比較実測していない。[Sources] ../threat-model.md「系統4: nas」「選定時に残る条件と負担」「操作審査とモデル入力」 [/Sources] -->

1. エージェントに編集させるファイルと、書込みを禁止する設定

## 付録・秘密情報を隠す設定

利用者が、各構成で使える機能に合わせて読取禁止や値の置換を設定する。

| 作業での使い方 | 用意する対策 |
| --- | --- |
| 作業で使わない秘密情報 | ファイルを共有から外すか、読取りを禁止する |
| HTTP認証に本物のtokenが必要 | 対応するproxyで、ダミーtokenを送信時に本物へ置き換える |
| 設定ファイルは必要だが、本物の値は不要 | マスク機能でファイルの形を残し、秘密の値だけをダミーにする |
| ツール出力に秘密が含まれる | 出力のマスク処理で、モデルに渡す前に秘密の値を伏せる |

<!-- notes: 利用できる保護機能は構成によって異なる。HTTP(S)以外の処理で本物が必要な場合は、今回の構成ではその値をエージェントから隠せない。Gitのindexや履歴に秘密があれば差分やgit showにも現れるため、読めない構成にするには渡す履歴にも本物を含めない。[Sources] ../threat-model.md「シークレットと作業領域」 [/Sources] -->

## 付録・CIからの本番操作

CIの権限と承認設定は5構成に共通する導入条件とし、比較表では採点しない。

CIに本番用の権限を渡さないか、本番操作の前に人間の承認を必須にする。承認設定は、エージェントが編集できるworkflowの外で管理する。

```d2
vars: { d2-config: { layout-engine: tala } }
direction: right
agent: エージェント {
  style.fill: "#edf3fa"
  style.font-size: 28
}
ci: CI {
  style.fill: "#edf3fa"
  style.font-size: 28
}
approval: 人間の承認 {
  style.fill: "#fcf0dc"
  style.font-size: 28
}
production: 本番変更・公開 {
  style.fill: "#fbedeb"
  style.font-size: 28
}
agent -> ci: コードを更新 { style.font-size: 26 }
ci -> approval: 本番操作を保留 { style.font-size: 26 }
approval -> production: 承認後 { style.font-size: 26 }
```
